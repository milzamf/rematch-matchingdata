## Prosedur operasional yang disiapkan (belum boleh dijalankan pada utama)

1. Tetapkan release/commit dan operator; verifikasi guard deployment, kompatibilitas versi MySQL, semua writer legacy/queue/autosave, serta ruang disk untuk backup, sidecar lineage, indeks dan temporary DDL. Jangan menjadikan benchmark fixture sebagai SLA produksi.
2. Aktifkan freeze marker/config secara seragam pada HTTP dan queue; marker `storage/framework/review-write.freeze` harus berada pada volume bersama. Mode ini menahan semua API bisnis, termasuk GET yang dapat membangun cache/index. Drain request berjalan dan seluruh jenis queue, hentikan worker lama, verifikasi tidak ada writer aktif sebelum backup/DDL/backfill. Admission fence bukan pengganti drain; jangan meninggalkan worker lama dengan config stale saat marker dihapus. Catat posisi binlog/GTID dan versi state/configuration. Jangan mengandalkan flag UI untuk fencing.
3. Buat backup konsisten seluruh database InnoDB (termasuk trigger, routine, event), file sumber dan sidecar/checkpoint, konfigurasi serta release lama. Verifikasi checksum, lalu restore ke DB terisolasi dan validasi jumlah/fingerprint histori serta sampel key `001`/`1`. Backup belum teruji restore bukan gerbang yang lulus.
4. Tetapkan `lock_wait_timeout` bounded; cek transaksi panjang dan metadata lock. Terapkan migrasi additive yang telah direhearsal satu per satu saat writer fenced. Jangan melakukan rollback foundation pada tabel populated atau menonaktifkan foreign keys untuk memaksanya. Catat durasi aktual; batalkan jika lock/kapasitas melewati anggaran.
5. Audit source hash/parser/lineage dan dry-run setiap job. Periksa collision, unknown reviewer, Undo dan histori ambigu. Apply shadow backfill chunk/checkpoint dengan resume, tanpa similarity rerun/rewriting histori/pemilihan pemenang; tahan hanya record/acuan bermasalah. Isi proyeksi skor secara bounded. Validasi cardinality, orphan/FK, unique record/entity claims, actor provenance, keputusan/statistik dan histori sebelum ready.
6. Hanya job completed/schema-1 yang lolos validasi boleh ready. Hold lokal/pending review biasa tidak memblokir seluruh job; snapshot stale, migrasi/backfill tidak lengkap atau integritas database global gagal menahan write. Jangan mencampur reader lama dan baru.
7. Setelah persetujuan GO, aktifkan backend writer/reader bersama dan frontend yang sesuai, invalidate cache/session permissions dan lakukan smoke Owner/Admin/Editor/Viewer/Pimpinan. Buka writer baru secara terkendali; monitor 409, 403/revocation, latency, lock waits, DB/RAM/disk serta export completeness. Tidak ada auto retry konflik keputusan.
8. Sebelum write baru, rollback dapat kembali ke release lama dengan writer tetap fenced dan shadow ledger rollback terverifikasi. Setelah write baru, jangan sekadar mematikan flag: freeze lagi, backup delta/operation/history, tentukan recovery point dan rekonsiliasi keputusan baru. Restore backup hanya dengan persetujuan loss window dan replay yang terbukti; jika tidak, forward-fix. Reader baru dimatikan sebelum menghapus projection; foundation/schema populated tetap dipertahankan.
